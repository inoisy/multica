# ТЗ: модели агента — профили моделей, выбор на сервере multica

Версия 3 · 19.10.2026 · логика в форке multica (как в версии 2); профиль — отдельная сущность, агенты и задачи
ссылаются на него; профиль на задачу, «когда всё на лимите» и уведомление о простое — решения Евгения 19.10.2026.
Версия 1 (пульт и сторож как писатель) и версия 2 (профиль-шаблон) — в истории git.

## 1. Цель

Задача проходит путь от назначения до слияния в `main` без человека и без простоев, не теряя в качестве.
Мерило — STT-258: работы около 2,5 ч, пути почти трое суток. Время ушло на ожидание после лимитов
(30–70 мин на каждом падении, 17–18.10 почти сутки), на 15 ранов Тимлида (почти все пустые) и на ночные паузы.
Качество держат шаги QA и review маршрута и приёмка ветки перед слиянием — они остаются.

Принципы:

- **провайдер меняется только списком моделей** — профиля (агента или задачи) или своего списка агента; других
  механизмов смены модели нет;
- **один писатель** — backend multica; сторож, пульт и CLI модель агента не пишут;
- **профиль — ссылка, а не копия**: поправил профиль — поменялось у всех агентов и задач, которые на него ссылаются;
  свой список у агента — явное исключение;
- **просто**: нет режимов «авто/закреплено» и переопределений вне профилей — закрепление = список из одной строки,
  сила на задачу = профиль на задаче.

## 2. Что убираем

| что | где сейчас | судьба |
|---|---|---|
| Полоса провайдеров сторожа (`apply_profile`, остывания, будильники, rerun по квоте) | `multica-conveyor`, `multica-provider.timer` | выключается на этапе 2, код удаляется |
| Переопределения эпика (`epics[].overrides`, `override_levels`) | конфиг сторожа | заменяются профилем на задаче (раздел 3) |
| Цепочки и режимы агентов, свои профили | `controls.json`, пульт `multica-control` :8098 | переносятся в БД multica (раздел 7), API пульта для них удаляется |
| `mconv` (профили, цепочки, режимы) | `/usr/local/bin/mconv` | заменяется `multica agent models`; команды конвейера эпиков (`board`/`target`/`pause`) остаются, пока жив сторож |
| `multica-fallback` | таймер выключен с 16.10.2026 | удаляется |
| Штатные поля агента runtime/модель/рассуждение как отдельный ввод | экран агента | становятся первой строкой списка (раздел 5) |

Остаётся снаружи без изменений: `subs-pick` и обёртки провайдеров (какой аккаунт внутри runtime), дашборд квот (для людей),
приёмка и слияние веток в стороже (позже — шаг `close` маршрута, отдельной задачей).

## 3. Модель данных (форк `inoisy/multica`, аддитивная миграция)

**Профиль** — `model_profile`, отдельная сущность workspace:

| поле | смысл |
|---|---|
| `id`, `workspace_id` | профиль принадлежит workspace (runtime в его строках — этого workspace) |
| `name`, `description` | «Сильная — сложная разработка и ревью»; имя уникально в workspace |
| `when_exhausted_profile_id` | все модели профиля на лимите: пусто — ран ждёт сброса (как сейчас); задан — берётся список этого профиля («лучше слабее, чем стоять»); цепочка профилей без циклов, проверка при сохранении |

Строки профиля — `model_profile_option`: `profile_id`, `position` (1 — основная), `runtime_id`, `model`,
`thinking_level` (пусто — дефолт runtime), `custom_args` (пусто — выводятся, раздел 4, п. 5).

**У агента:**

- `model_profile_id` — ссылка на профиль; обычный случай;
- `agent_model_option` (те же поля, что у строки профиля) — **свой список**, только как исключение. Есть строки — профиль
  агента не используется, в интерфейсе «своя цепочка, отличается от профиля». Список из одной строки = модель закреплена;
- нет ни профиля, ни своего списка — агент работает как сейчас, по штатным полям.

**У задачи** — `issue.model_profile_id`, необязательно. Ставит Тимлид или человек («эта задача сложная»). Раны этой
задачи у любого агента выбирают модель из профиля задачи вместо профиля или своего списка агента; другие задачи агента
не затрагиваются — модель выбирается на каждый ран при claim, агента менять не нужно.

Удаление профиля, на который ссылаются агенты или открытые задачи, запрещено, пока их не переведут.

**Недоступность runtime** — `runtime_unavailable`: `runtime_id`, `until`, `reason`, `task_id` (ран, на котором упало).
Пишет только backend.

**У рана** (`agent_task_queue`): `model_position`, `model`, `thinking_level`, `custom_args` — что фактически выбрано
при claim; для диагностики и повтора.

## 4. Логика

0. **Какой список.** Профиль задачи, если задан → свой список агента, если есть → профиль агента → штатные поля агента.
1. **Выбор при claim, а не при постановке.** Демон забирает ран → backend берёт первую строку этого списка, чей runtime
   обслуживается этим демоном, онлайн и не в `runtime_unavailable` → пишет выбор в ран и отдаёт его демону.
   Сейчас runtime фиксируется при постановке (8 мест в `service/task.go` берут `agent.RuntimeID`), а модель —
   из агента при claim (`handler/daemon.go`, сборка `AgentData`). Отсюда «вечные queued» на runtime, с которого агента
   увели, и риск отдать модель одного семейства в runtime другого. Ран ставится на агента; runtime определяется при claim.
2. **Лимит — сразу следующая модель.** Ран завершился с `failure_reason` квоты/ёмкости провайдера (классификатор
   STT-258, `taskfailure.Classify`; сюда же мгновенный отказ `subs-pick` «подписки runtime выше лимита агентам») →
   в той же транзакции `OnTaskTerminal`: runtime в `runtime_unavailable` до сброса из текста ошибки (z.ai — UTC+8),
   без времени — на 60 мин; тот же ран ставится повтором (`rerun_of_task_id`, тот же `conveyor_action_id`), при claim
   ему достанется следующая модель. Цена — один упавший за секунды ран вместо ожидания.
3. **Весь список недоступен** — если список взят из профиля и у профиля задан `when_exhausted_profile_id`, берётся его список (рекурсивно,
   без циклов), в причине выбора — «все модели „Сильной“ на лимите, взята „Выше среднего“». Иначе ран ждёт в очереди
   со статусом «все модели на лимите до HH:MM»; scheduler
   (`server/internal/scheduler`, по образцу `jobs_issue_conveyor.go`) снимает просроченные записи `runtime_unavailable`,
   и ран забирается сам. Ни внешнего rerun, ни будильников. У своего списка агента запасного профиля нет — ждёт.
4. **Возврат на основную** — сам собой: каждый новый ран берёт первую доступную строку, то есть основную, как только она
   снова доступна, в том числе посреди задачи (решение Евгения 19.10.2026). Отдельного «вернуть через N минут» нет.
   Правка профиля действует так же: со следующего рана у всех, кто на него ссылается.
4а. **Уведомление о простое.** Ран агента встал «все модели на лимите» (и запасного профиля нет) — backend один раз шлёт
   владельцу workspace уведомление во входящие multica: агент, задача, до какого времени, какие runtime упёрлись.
   Повтор — только после выхода из простоя и нового входа; выход — короткое «агент снова работает». Пишется
   в той же транзакции, что и постановка рана в ожидание; дедуп по агенту и эпизоду простоя.
5. **`custom_args`** — пустые у строки → backend выводит их для семейства runtime из запретов агента: запреты задаются
   один раз на агента (список `сервер:инструмент`), backend рендерит `--disallowedTools …` для claude и
   `-c mcp_servers.<сервер>.disabled_tools=[…]` для codex. Явные `custom_args` строки — как есть, без перевода.
6. **Серверный маршрут STT-258 по умолчанию** — у сквада шаблон маршрута (`dev:…,qa:…,review:…,close:…`); при
   назначении задачи скваду маршрут включается сам, если его у задачи нет. Тимлид будится только на неоднозначный
   результат и возврат. Сторож маршрут не ведёт (временный пропуск — отдельная правка сторожа до этапа 2).
7. **Права** — профиль и свой список агента правят владелец агента и admin/owner workspace, как штатные поля агента
   сейчас; профили workspace (создать, править, удалить) — admin/owner; профиль на задаче ставит тот, кто может
   править задачу.

## 5. Интерфейс

Сейчас модель задаётся в двух местах: штатные поля runtime/модель/рассуждение в «Общее» и ниже блок «Фоллбек-модели»
(режим «авто/закреплено», аргументы свободным текстом на каждую модель, «применится после рана», порог профиля).
Становится одно место.

### Экран агента → «Настройки → Общее → Модели»

- **Профиль** — выпадающий список профилей workspace; рядом «открыть профиль» с предупреждением «правка затронет N
  агентов и M задач».
- **Сейчас** — карточка: какая строка выбрана для последнего рана, runtime, модель, рассуждение, подписка
  (последняя строка `choice.log` этого runtime, если есть), источник (`профиль „Сильная“` / `своя цепочка` /
  `профиль задачи STT-NNN`) и причина одной фразой: «основная», «1-я на лимите до 15:53 — взята 2-я»,
  «все модели „Сильной“ на лимите — взята „Выше среднего“», «все на лимите до 15:53 — ран ждёт».
- **Модели профиля** — строки профиля только для чтения: номер (1 — «Основная»), runtime, модель, рассуждение,
  состояние (`доступна` / `на лимите до 15:53` / `runtime офлайн`), отметка текущей. У строки «Закрепить» —
  создаёт свой список из одной этой строки.
- **Своя цепочка** — переключатель «Отличается от профиля». Включён — список становится редактируемым: перетаскивание
  или ↑/↓, удалить, «+ Добавить модель»; модель и рассуждение — из каталога runtime (`runtime_models`), не свободным
  текстом; при включении заполняется копией строк профиля. Выключен — свой список удаляется, агент снова на профиле.
  Сохранение действует со следующего рана; идущий ран не трогается по построению.
- **Запреты инструментов** — один список на агента, чипы `сервер:инструмент`; «Аргументы» строки скрыты под
  «Дополнительно» и нужны только для исключений.
- **Задачи со своим профилем** — открытые задачи агента с `model_profile_id`: задача, профиль.
- **Журнал** — последние 10 выборов: время, задача, строка, источник, причина.

### Страница «Профили» (рядом с «Подписками»)

Таблица: имя, модели по порядку (компактно `codex·sol·high → claude·opus → glm`), «когда всё на лимите»
(`ждать` / профиль), кто ссылается (агенты; открытые задачи; отдельно — агенты со своей цепочкой, заполненной из этого
профиля). Правка профиля — с предпросмотром «у кого сменится основная модель» и сохраняется для всех ссылающихся сразу.
«Создать профиль» — с нуля или из списка агента.

### Задача

В карточке задачи — поле «Профиль модели» (по умолчанию пусто: профиль исполнителя). Видно и в CLI.

### Без профиля

Профиль не обязателен: «Своя цепочка» собирает список с нуля, одна строка — просто выбранная модель без фоллбеков.

### Страница «Подписки»

Остаётся как есть: таблицы подписок, runtime (какие подписки за ним и порядок трат) и окон квот, правка — владелец,
журнал; аккаунт на ран по-прежнему выбирает `subs-pick` по этим таблицам. Меняется одно: в таблице runtime колонка
«агенты» берётся из списков моделей (строки профилей агентов и `agent_model_option`) — у каких агентов runtime в списке и у кого он сейчас
выбран, плюс отметка из `runtime_unavailable` «на лимите до HH:MM». Отказ `subs-pick` («выше лимита агентам»)
backend считает квотой (раздел 4, п. 2) — так лимит, выставленный на этой странице, сам уводит агентов на следующую модель.

### Страница «Конвейер»

Остаётся доской эпиков: цели, стадии, задачи, пауза конвейера и целей, журнал — пока приёмку и слияние веток ведёт
сторож. Меняется:

- блок «агенты и их провайдер» берёт текущую модель из backend (карточка «Сейчас» экрана агента), а не из пульта;
  кнопки смены цепочки на этой странице нет — только ссылка на «Модели» агента;
- у задачи — шаг серверного маршрута (`dev`/`qa`/`review`/`close`, статус `waiting_provider` с «до HH:MM»)
  из `GET /api/issues/{id}/conveyor` вместо `metadata.route`;
- события «сторож сменил провайдера» и «повтор после лимита» из журнала уходят — их заменяет журнал выбора модели агента.

Когда приёмка переедет в шаг `close` маршрута (отдельная задача), доска переходит на данные backend целиком,
и пульт `multica-control` выключается.

### CLI

`multica agent models <агент>` — список, состояние, текущий выбор, источник и причина; `multica agent models profile <агент>
<профиль>`; `multica agent models set <агент> <runtime>[:<модель>[:<рассуждение>]] …` (своя цепочка) и `… reset` (снова
на профиль); `multica issue model-profile <задача> <профиль>|off`; `multica profile list|show|create|edit|delete`;
`multica runtime unavailable` — текущие записи недоступности.

## 6. Этапы

1. **Backend, только чтение.** Миграция, таблицы (профили, строки, свой список агента, профиль задачи), функция выбора;
   CLI `models` показывает, что выбрал бы сервер; claim по-старому. Импорт из `controls.json` (раздел 7) сухим прогоном.
2. **Включение.** Claim выбирает по списку, квота обрабатывается в `OnTaskTerminal`, ран ставится на агента без
   runtime, запасной профиль и уведомление о простое работают. Полоса провайдеров сторожа и `multica-provider.timer` выключаются в том же окне; откат — пакет как у STT-258.
3. **Веб.** Экран «Модели», страница «Профили» и поле профиля в задаче на штатном API; старый блок фоллбеков
   и страница пульта удаляются.
4. **Маршрут по умолчанию** у сквада и уборка: профильная часть `mconv`, цепочки в пульте, `multica-fallback`.
5. **Вход в подписки из интерфейса** (раздел 10). От этапов 1–4 не зависит, можно делать параллельно, если не трогает
   те же файлы веба.

Каждый этап — свой PR в форк от предыдущего, свой пакет установки и отката.

## 7. Перенос текущего состояния

- Профили (`providers.tiers`, свои из `controls.json → tiers`) → `model_profile` в каждом workspace, где есть runtime
  их видов; `kind` строки → `runtime_id` этого workspace (как `control_state.resolve`).
- Цепочка агента (`controls.json → chains`, иначе `providers.agents` конфига сторожа) совпадает со строками его профиля
  (`chains.<id>.tier`) → у агента только `model_profile_id`. Не совпадает → `model_profile_id` плюс свой список
  (`agent_model_option`); список таких агентов — в отчёт, решение по каждому за Евгением.
  Режим «закреплён N» → свой список из одной N-й строки (в отчёт).
- `custom_args` строк → запреты агента (объединение); расхождения между строками — в отчёт.
- Переопределения эпиков (`epics[].overrides`) открытых задач → `issue.model_profile_id` на профиль с той же моделью
  и рассуждением; нет такого — в отчёт. Закрытых — не переносятся.
- `when_exhausted_profile_id` — пусто у всех (поведение не меняется).
- Сухой прогон: для каждого агента — текущая модель и что выбрал бы сервер; расхождения без объяснения — 0.

## 8. Приёмка

Команды, а не слова:

- `go test ./internal/service ./internal/handler ./internal/scheduler -run 'ModelOption|ModelProfile|Claim|Quota|Idle'` на реальной
  PostgreSQL, демоны подменены, реальных агентских запусков нет:
  - claim берёт первую доступную строку; строка с runtime не этого демона пропускается;
  - падение на квоте → `runtime_unavailable` + ровно один повтор; при claim — следующая строка;
  - отказ `subs-pick` («выше лимита агентам») = квота;
  - обычный сбой с «429»/«quota» в тексте и явной не-квотной причиной — не квота (как в STT-258);
  - весь список недоступен → ран ждёт, после истечения `until` забирается без внешнего вызова;
  - основная снова доступна → следующий ран на основной;
  - правка строк профиля → следующий claim у всех агентов на этом профиле берёт новые строки; агент со своим списком —
    не меняется;
  - профиль задачи: ран задачи с профилем берёт его строки, ран другой задачи того же агента — профиль агента;
  - все строки на лимите и задан запасной профиль → строка запасного; цикл профилей при сохранении — ошибка 400;
  - уведомление о простое: одно на эпизод, «снова работает» — одно при выходе, повторный вход — новое;
  - удаление профиля со ссылками — ошибка, без ссылок — удаляется;
  - смена списка не трогает идущий ран; два одинаковых прогона scheduler — 0 изменений;
  - запреты рендерятся одинаково по смыслу для claude и codex;
  - права: не владелец и не admin список не меняет.
- После этапа 2 сторож не меняет модель агента: `grep -nE "apply_profile|agent', 'update'" services/multica-conveyor/multica-conveyor` — 0.
- Веб на стенде: скриншоты 1440px — агент на профиле, «на лимите — взята 2-я», «все на лимите», «взят запасной профиль»,
  своя цепочка, страница «Профили» с предпросмотром правки, профиль в карточке задачи.
- Сутки журнала после этапа 2: ни одного рана, ждавшего лимита дольше сброса окна; на один runtime подряд — не больше
  одного падения на квоте до его `until`.

## 9. Решённые вопросы

1. **Модель на уровне рана** — в multica её нет (проверено по форку: runtime при постановке, модель из агента при claim).
   Решение — выбор при claim с записью в ран (раздел 4, п. 1). Благодаря этому профиль на задаче не меняет агента.
2. **Профиль — ссылка или шаблон** — ссылка (Евгений, 19.10.2026): шаблон затирает список агента и не доходит
   до агентов при правке. Свой список агента — явное исключение.
3. **Сила на задачу** — профиль на задаче (Евгений, 19.10.2026), вместо `epics[].overrides`.
4. **Лучшая модель освободилась посреди задачи** — переход на следующем же ране (Евгений, 19.10.2026).
5. **Всё на лимите** — настройка профиля: ждать (по умолчанию) или запасной профиль (Евгений, 19.10.2026).
6. **Уведомление о простое** — в первой версии (Евгений, 19.10.2026); канал — входящие multica владельцу workspace.
7. **Уровень на роль в скваде** — нет; профиль на агента, массово — правкой профиля.
8. **Подписки в профиле** — нет; аккаунт внутри runtime выбирает `subs-pick`, его отказ backend считает квотой.
9. **Профили на workspace или общие** — на workspace: строки ссылаются на runtime, а runtime у каждого workspace свои.

Не входит в первую версию: выключение модели во всех профилях сразу, закрепление со сроком.

## 10. Вход в подписки из интерфейса

Сейчас перелогин — по ssh от agents (`CODEX_HOME=~/.codex-reserve codex login --device-auth`, код пересылается владельцу
подписки; токен Claude — `claude setup-token` и файл руками). Цель — кнопка на странице «Подписки».

### Интерфейс

У карточки аккаунта на «Подписках»:

- **Статус входа** — «вошли» / «токен отозван» / «не входили» / «проверка не удалась»; Codex — `codex login status`
  в его `CODEX_HOME`, Claude — проба в 1 токен, как в `subs-pick`, ключи API — запрос квоты провайдера.
- **«Войти заново»** — окно входа:
  - Codex (device-auth): ссылка и код, «Скопировать для владельца»; окно само ждёт завершения и показывает
    «вошли, неделя N %»;
  - Claude (подписка): ссылка из `claude setup-token` и поле «Вставьте код из браузера»; запасной путь — поле
    «Вставить готовый токен» (владелец делает `claude setup-token` у себя);
  - ключ API (z.ai, MiniMax, OpenRouter): поле «Новый ключ» и проверка запросом квоты.
- Кнопка только у владельца workspace; в журнале «Подписок» — кто, когда, какой аккаунт, результат. Значения
  ключей и токенов нигде не показываются и не пишутся: ни в БД, ни в журнал, ни в ответы API.

### Исполнитель — хостовый помощник, не backend

Файлы входа принадлежат agents (`~agents/.codex-reserve/auth.json`, `~agents/.config/<провайдер>/token|key`),
backend-контейнер к ним доступа не получает. Помощник `subs-login` (systemd, User=agents, слушает 127.0.0.1)
по образцу `stand-feedback`: проверяет сессию multica (`/api/me`) и роль owner workspace; страница «Подписки» ходит
к нему через Caddy (`handle_path /subs-login/*` в блоке multica, бэкап Caddyfile перед правкой).

- Вход идёт во временный каталог (`CODEX_HOME=$(mktemp -d)` / временный файл токена); после успешной проверки —
  атомарная подмена рабочего файла (`rename`), права 600. Брошенный или неудачный вход рабочую подписку не трогает;
  незавершённый вход убивается через 15 мин, каталог удаляется.
- Один вход на аккаунт одновременно; второй запрос получает текущее окно.
- Путь к файлу берётся из таблицы «Подписок» (там уже хранится путь учётки), не из запроса.
- Источник — `inoisy/monorepo-for-multica`, рядом с пультом; веб — патч страницы «Подписки» в форке.

### Проверить до разработки

- `claude setup-token` — терминальный интерфейс: принимает ли код через псевдотерминал на сервере без браузера.
  Не принимает — для Claude только «Вставить готовый токен».
- `codex login --device-auth` в `codex-cli` 0.163: формат вывода ссылки и кода, код выхода при отмене и таймауте.

### Приёмка

- Тесты помощника с подменёнными `codex`/`claude`: успешный вход подменяет файл; отмена, таймаут, неверный код —
  рабочий файл байт в байт прежний; не owner — 403; второй одновременный вход — то же окно; в логах и ответах
  нет значения токена (`grep` по журналу тестового прогона — 0).
- На сервере: перелогин `codex-second` из интерфейса, `codex login status` в его `CODEX_HOME` — «Logged in»,
  `subs-pick` берёт аккаунт на следующем ране.
