# Маршрут сам разбирает механические сбои

Координатора (`close`) маршрут будит, когда нужно решение. Три случая, где решения не было, сервер с 22.10.2026
разбирает сам. Случай — STT-368: из 10 ранов задачи четыре ушли на такие сбои.

## Ран оборвала инфраструктура — шаг стартует снова

Ран шага кончился сбоем инфраструктуры, а не работы: демон остановлен или перезапущен (`cancelled`), runtime
офлайн или не переподключился, ран истёк в очереди, idle-watchdog, сбой провайдера на его стороне (5xx, сеть).
Тогда сервер открывает новый раунд того же шага (решение `retry` в журнале); принятый коммит сохраняется.
Отмена человеком (`user_cancelled`) и ошибка самой работы не повторяются.

Сколько раз — параметр шага `retries=N` (0..5, по умолчанию 2) на ревизию маршрута; кончились — координатор,
в причине «N retr(ies) spent».

## Ручной Retry после эскалации

Если упал ран шага и маршрут уже ждёт координатора, после завершения рана координатора можно повторить
упавший шаг через Retry или `multica issue rerun <KEY> --task <ран шага>`. Без `--task` повторяется текущий
упавший шаг. Повтор привязывается к тому же шагу и раунду, сохраняет принятый коммит и получает инструкции
сдачи результата. После его успешного завершения сервер запускает следующий шаг.

Если такой повтор уже работает отдельно от маршрута, повторная команда подхватывает его без нового рана.
Для подхвата нужны те же права на запуск агента. Пока координатор ещё выполняется или ожидает запуска,
Retry шага возвращает конфликт, чтобы не запускать одновременно два решения по одному маршруту.

## Проверяющий сам поправил — маршрут идёт вперёд

Проверяющий (`qa`, `review`) сдаёт `pass` со своим коммитом поверх принятого. Сервер делает этот коммит
принятым и ведёт маршрут к следующему шагу: без возврата в `dev`, без повторных `qa`/`review` и без
координатора. В журнале — решение `advance` с причиной «accepted commit advanced by <шаг>: X → Y».
Страховка — шаг `accept`: он гоняет команды `.multica/acceptance.json` на результате слияния принятого
коммита. (С 22.10.2026, форк PR #38; раньше — повторная проверка `recheck` с первого проверяющего, #33.)

## Фикс красной приёмки — сразу на `accept`

`accept` сдал `changes_requested` — работа уходит в `dev` (`back` по умолчанию, ниже). Когда `dev` сдаёт
фикс, маршрут идёт сразу на `accept`, а не через `qa` → `review`: проверяющие работу уже прошли, а
приёмка проверит слияние целиком (STT-354: переименование ADR после красной приёмки). В журнале —
«accept retry: dev → accept». У шага `dev` с несколькими исполнителями фикс проходит по оставшимся
исполнителям шага и потом — на `accept`. `changes_requested` от `qa` или `review` по-прежнему ведёт
`dev → qa → review`.

## `back` у проверяющих по умолчанию

`qa`, `review` и `accept` без `back` возвращают `changes_requested` на ближайший предыдущий рабочий шаг
(`dev,qa,review,accept`: `dev`), с `rounds` по умолчанию 2. `back=none` — по-старому, к координатору.
Красная приёмка (`pnpm check`, конфликт с базой) уходит исполнителю `dev` с хвостом лога.
