## Соответствие и расхождения

| Понятие RFC | Наш текущий код / целевая STT-433 |
| --- | --- |
| Привязка выполнения | Упорядоченная строка `model_profile_option`: runtime, модель, рассуждение. Это соответствие по смыслу, не реализация таблицы `agent_binding` |
| Проекция primary binding | Поля агента должны стать копией строки 1; сейчас автоматическая синхронизация не обеспечена |
| Свежий выбор и снимок попытки | `PreviewChoice`, claim, `model_choice`, предложение и подтверждение аккаунта |
| Идентичность пула квоты | Явные `subscription` и `subscription_pool`; выдача workspace, cap на окно |
| Политики владельца / shared pool | Нельзя считать их реализованными только из-за наличия пулов аккаунтов; наша модель выдачи отличается |

## Порядок вклада

Решение Евгения 26.10: сначала довести STT-433. Затем обновить данные черновика
из STT-435 и согласовать текст. После ответа мейнтейнеров предлагать небольшие
PR: телеметрия, факт аккаунта попытки, история выполнения. Не дублировать работу
открытых PR и не публиковать внутренние адреса, имена аккаунтов или пути входа.
Источник: [STT-435](https://multica.yakutov.com/stt/issues/STT-435).

При переносе сверять миграции и правила апстрима: без FK, каждый concurrent
индекс отдельным файлом, API-совместимость через zod. Исходная точка этих правил
в форке — [AGENTS.md](../../../AGENTS.md); перед внешним PR перечитать правила
текущего upstream HEAD. В STT-436 внешние комментарии и PR в апстрим не создаются.
