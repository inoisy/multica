# ТЗ: конвейер целиком в multica — приёмка шагом маршрута, стадии на сервере, сторож удаляется

Версия 1 · 19.10.2026 · продолжение `tz-model-tiers.md` (этапы 1–4). Решение Евгения 19.10.2026: внешнего сторожа
(`monorepo-for-multica/services/multica-conveyor`) не остаётся; всё, что он делает, — в форке multica (сервер и демон),
переносимо на любой хост с демоном; автоприёмка сторожа в нынешнем виде не годится.

## 1. Цель

Задача проходит от назначения до слияния в базовую ветку без человека и без внешних скриптов: маршрут multica ведёт
шаги, демон multica выполняет приёмку, сервер назначает стадии эпика. Всё видно в multica (журнал маршрута, задача,
раны), переносится вместе с multica, ставится и откатывается одной сборкой.

Чем плоха нынешняя автоприёмка (почему не переносим её как есть):

- живёт вне multica: cron-скрипт на одном хосте, своё состояние (`state.json`, файлы задач atd), своя страница статуса;
- берёт «что вливать» из `metadata.branch/commit`, которые пишет агент, а не из результата шагов маршрута;
- вливает в базу прямым `git merge` на хосте, мимо истории multica; итог виден только в журнале сторожа;
- review и проверка — разные источники правды: review одобрил один коммит, сторож проверяет тот, что в metadata.

## 2. Что остаётся и что меняется

| что делает сторож | куда переезжает |
|---|---|
| ведение маршрута | уже на сервере (STT-258, этап 4) |
| приёмка: проверка коммита поверх базы и слияние | шаг маршрута `accept`, исполняет демон без модели (раздел 3) |
| смена провайдера и повтор после квоты | уже на сервере (этап 2 ТЗ моделей) |
| уровни рассуждения на задачу (`overrides`) | уже профиль модели на задаче (этап 3 ТЗ моделей) |
| стадии эпика: назначить следующую, когда закрыта текущая | сервер (раздел 4) |
| «**Ждёт:**» в описании | статус задачи «ждёт заказчика» (раздел 4) |
| автоповтор после инфраструктурного падения | штатный повтор multica (`MaybeRetryFailedTask`), расширить причины (раздел 5) |
| загрузка справочников стенда rp после пересборки | сам стенд при старте, не multica (раздел 6) |
| страница статуса | экраны multica: эпик, маршрут, агенты (раздел 7) |

## 3. Приёмка — шаг `accept` маршрута

### Исполнитель

Новый провайдер демона `accept` (рядом с claude, codex…, `pkg/agent`), **без модели**. Демон регистрирует его runtime
всегда (не ищет CLI). Агент «Приёмщик» — обычный агент workspace на этом runtime; маршрут сквада:
`dev:Бэкенд,qa:Тестировщик,review:Техдиректор,accept:Приёмщик,close:Тимлид`. Модель, профиль и подписки к нему не
применяются (выбор модели его пропускает).

### Что делает ран `accept`

1. Берёт из контекста маршрута (`task_context.conveyor`) принятый коммит маршрута (`accepted_commit` — коммит, который
   прошли dev, qa и review; не metadata задачи) и репозиторий шага dev (`artifact.repo`, `artifact.branch`).
2. Готовит чистую копию через кэш репозиториев демона (`repocache`), как `multica repo checkout`: коммит, поверх —
   текущая вершина базовой ветки (`git merge --no-ff`, без push). Конфликт — итог `fail` с причиной «конфликт с базой».
3. Проверяет дифф (запреты как у сторожа: `as any`, `@ts-ignore`, `eslint-disable`… — список в файле проекта).
4. Выполняет команды приёмки из файла **в самом репозитории** — `.multica/acceptance.json` в проверяемом коммите:
   `{"base": "main", "commands": [...], "timeout_seconds": 1500, "env": {...}, "busy_exit_codes": [75],
   "wait_poll_seconds": 60, "wait_max_seconds": 7200, "diff_guard": [...]}`. Файла нет — `fail` «нет описания приёмки».
   Команды живут с кодом: меняются в том же PR, ревьюятся, переносятся с репозиторием.
5. Код «ресурс занят» — ждёт и повторяет, ожидание не входит в таймаут; не дождался — итог `blocked` с причиной
   (маршрут ставит `waiting_provider`-подобное ожидание и повторяет шаг позже, лидера не будит).
6. Зелёно — вливает ровно проверенный merge-коммит в базу (`git push` базовой ветки с проверкой, что база не сдвинулась;
   сдвинулась — повтор с шага 2, не более 3 раз). Красно — итог `changes_requested`: хвост лога в отчёте, слияния нет,
   маршрут будит координатора (как любой непройденный шаг; возврат на `dev` решает он).
7. Отчитывается штатно: `conveyor result` с `checks[]` (каждая команда — строка), `artifact.commit` = влитый коммит;
   полный лог — в сообщениях рана (виден в multica, токены вырезаются).

### Правила на сервере

- Шаг `accept` в маршруте — один раз, не первым, прямо перед `close` (с 22.10.2026 `review` перед ним не обязателен); проверяется при включении
  маршрута и при сохранении шаблона сквада.
- `accept` проверяет `accepted_commit`; другой коммит в результате — эскалация, как у qa/review сейчас.
- Два `accept` одной базы одновременно не вливают непроверенное: push проходит, только если база не сдвинулась с
  начала проверки; иначе проверка повторяется на новой базе. Серверный замок `repo+base` не нужен (решено при
  реализации этапа 1: оптимистичный push проще и даёт ту же гарантию).
- Права на push: учётные данные git хоста демона, те же, что для клона (решение Евгения 19.10.2026: прямой push,
  любой демон). Агенту-модели они не нужны.

### Чем это лучше нынешнего

Проверяется и вливается ровно то, что прошли review и qa; итог и лог — в multica; нет cron, atd, `state.json`;
переносится с демоном; команды приёмки версионируются с кодом.

## 4. Стадии эпика на сервере

- У задачи-эпика флаг «вести стадии» и исполнитель-сквад стадий (`issue.stage_squad_id`, аддитивно).
- Когда все задачи стадии N закрыты (готово и, если в маршруте был `accept`, влиты — то есть маршрут `completed`;
  или отменены), сервер назначает скваду задачи следующей незакрытой стадии без исполнителя (по одной транзакции,
  не больше `max_per_stage` за раз). Назначение запускает маршрут сквада по шаблону (этап 4).
- Событие — уже существующее наблюдение `child_done` (`issue_wakeup_system.go`): оно знает о закрытии стадии.
- «Ждёт заказчика» — статус задачи (категория «не начата»), а не текст в описании: такая задача не держит следующие
  стадии и не назначается.
- Пауза эпика — тот же флаг выключен.
- Сделано (этап 2): флаг — `issue.stage_squad_id` (+ `stage_dispatch_by`, человек, включивший назначение);
  `multica issue stages <эпик> --squad …|--off`; статус «ждёт заказчика» — ключ `waiting`. Предела `max_per_stage`
  нет: открытая стадия назначается целиком (ограничивать нагрузку — профили моделей и очередь агентов). Подробно —
  `stage-dispatch.md`.

## 5. Автоповтор после инфраструктуры

Штатный повтор multica (`retryEligible`, `MaybeRetryFailedTask`) уже повторяет часть падений. Добавить причины, которые
сейчас повторяет сторож (`INFRA` в `multica-conveyor`: `initialize failed`, `handshake timeout`, `daemon restarted`,
`ECONNRESET`…), с тем же пределом подряд; после предела — эскалация маршрута лидеру (уже есть).

Сделано (этап 3): тексты `connection reset`, `handshake timeout`, `require-vless`, `routing discovery failed`,
`control protocol failed` классифицируются как `agent_error.provider_network` и повторяются штатно (до 3 попыток).
Голые `ECONNRESET`/`ETIMEDOUT` не добавлены: их печатают и локальные инструменты, и MCP-серверы, а апстрим нарочно
не повторяет такие падения. `initialize failed` и `process exited` остаются `process_failure` (без автоповтора):
по тексту не отличить сбой от детерминированного падения CLI. Шаг маршрута у подзадач — поле `route`
(`step`, `status`, `round`, `waiting_reason`) в `GET /api/issues/{id}/children` и колонка `STEP` в
`multica issue children --output table`; колонка в вебе — отдельной правкой веба.

## 6. Стенд rp

Загрузка справочников после пересборки — забота стенда: при старте, если справочники пустые, стенд сам вызывает
`/api/v1/sync/<source>`. В multica не переносится. (Отдельная задача в репозитории стенда.)

## 7. Страница статуса

Не нужна: эпик — задача-родитель со стадиями и маршрутами подзадач (шаг, статус, ожидание до HH:MM), агенты — экран
«Модели» (этап 3), квоты подписок — «Подписки». Недостающее — колонка «шаг маршрута» в списке подзадач эпика.

## 8. Этапы

Каждый этап — свой PR в форк от предыдущего, свой пакет установки и отката (как `deploy/stt-models`).

1. **Провайдер `accept` и шаг `accept`.** Демон: провайдер, подготовка копии, команды из `.multica/acceptance.json`,
   ожидание ресурса, слияние, отчёт. Сервер: правила шага, замок `repo+base`. Сторож продолжает работать, но для задач с
   шагом `accept` в маршруте не вливает (проверяет: `accept` в маршруте — пропуск).
2. **Стадии эпика на сервере** и статус «ждёт заказчика». Сторож перестаёт назначать стадии для эпиков с флагом.
3. **Автоповтор инфраструктуры** в multica; колонка шага маршрута у подзадач.
4. **Удаление сторожа**: таймеры выключаются, `multica-conveyor`, `control_state.py`, пульт `multica-control` и
   `migrate-routes` удаляются из монорепо; эпики из `/etc/multica-conveyor.json` переводятся на флаг стадий скриптом
   переноса (одноразовый, сухой прогон по умолчанию).

## 9. Приёмка

- Задача сквада «Разработка» с маршрутом `dev,qa,review,accept,close`: на каждый шаг ровно один ран; `accept`
  вливает ровно `accepted_commit` поверх базы; лидер будится один раз, на `close`.
- Красная проверка — возврат на `dev` с хвостом лога, слияния нет; конфликт с базой — то же с причиной.
- Ресурс занят — шаг ждёт, лидер не будится, таймаут не тратится.
- Две задачи одной базы на `accept` одновременно — вторая ждёт замок, проверяется поверх уже влитой первой.
- Стадия 1 эпика закрыта — задачи стадии 2 назначены скваду и пошли по маршруту без участия человека.
- `grep -r multica-conveyor` в монорепо после этапа 4 — только история.

## 10. Решённые вопросы (19.10.2026)

- Вливать прямым push merge-коммита в базу, не через PR.
- `accept` исполняет любой демон (runtime регистрируется всеми; выключить на хосте — `MULTICA_ACCEPT_RUNTIME=off`).
- Права на push — git-доступ хоста демона.
