# Шаг `accept`: приёмка и слияние маршрутом multica

> **26.10.2026 (STT-429): старый маршрут удалён.** Команды `multica issue conveyor enable/pause/resume/disable/get/events/result`,
> эндпоинты `/api/issues/{id}/conveyor*`, автозапуск по шаблону сквада и ретраи маршрута сняты. Приёмку выполняет шаг
> Workflow с обработчиком `accept` — `multica workflow accept` (`issue conveyor accept` — алиас на один релиз). Таблицы
> `issue_conveyor`, `issue_conveyor_event` и `route`/`step` в metadata закрытых задач остаются архивом. Ниже — история.

Этап 1 ТЗ `tz-conveyor-in-multica.md`. Шаг маршрута `accept` проверяет коммит, который прошли dev и проверяющие шаги (qa, review),
поверх текущей базовой ветки и вливает ровно проверенный merge-коммит прямым push. Выполняет его демон multica
без модели.

## Как это устроено

- Каждый демон регистрирует runtime `accept` (исполняемый файл — сам `multica`). Выключить на хосте:
  `MULTICA_ACCEPT_RUNTIME=off` в окружении демона.
- Шаг в маршрут не пишут: сервер, включая маршрут с `qa` или `review` и без `accept`, сам ставит `accept` прямо
  перед `close`. Нерискованная правка (`dev,qa,close`) вливается без Техдиректора; `review` нужен рискованной
  (`metadata.risky`). `metadata.accept` задачи решает за правило: `false` — не ставить, `true` — ставить в любой
  маршрут (проверяющий шаг со своим именем: `build,critic,close`).
  Исполняет его скрытый системный агент приёмки (`kind = 'system'`, `system_key = 'accept'`): сервер сам заводит его
  на онлайн-runtime `accept` workspace при первой надобности, в списках агентов и пикерах его нет, заводить и
  настраивать ничего не нужно. Ни один демон workspace не предлагает `accept` — маршрут идёт как записан. Явный `accept:<агент>` в маршруте по-прежнему допустим (один раз, не первым,
  прямо перед `close`).
- Приёмке нечего вливать — в маршруте нет принятого коммита или в репозитории нет `.multica/acceptance.json`
  (его вливают люди через MR) — шаг сдаёт `pass` без слияния и маршрут идёт к `close`.
- Упавшую команду приёмка запускает ещё раз (`retries` в `acceptance.json`, по умолчанию 1, до 3; `0` —
  один прогон): полный `pnpm check` на нагруженном сервере падал по таймауту каждый раз в другом тесте
  (STT-366), а настоящая регрессия красная на каждом прогоне. Зелёный повтор вливается, в итоге приёмки —
  «red on the first run, green on a retry: <команда>».
- Ход проверки (checkout, команды и их вывод) идёт в журнал рана по мере выполнения, а не в конце.
- Все шаги маршрута прошли — сервер сам закрывает задачу (`done`) и пишет системный итог: шаги, коммит, ветка, что
  сделала приёмка. Координатора (`close`) он будит только на эскалации: блокер, третий круг, красная проверка, сбой.
- Ран шага запускает `multica workflow accept` (старое имя `multica issue conveyor accept` — алиас на один релиз). Команда:
  1. берёт принятый коммит маршрута (`accepted_commit`) и репозиторий с веткой из прошедшего результата,
     который этот коммит назвал (`artifact.repo`, `artifact.branch` шага dev — **`artifact.repo` должен быть
     URL репозитория**, как для `multica repo checkout`);
     Путь локальной рабочей копии (как его пишут исполнители, работающие в worktree) приводится к репозиторию
     workspace: `origin` копии, а без него — основной репозиторий worktree;
  2. получает свежую копию через кэш репозиториев демона;
  3. читает `.multica/acceptance.json` из самого коммита;
  4. проверяет дифф, сливает коммит поверх `origin/<base>` (`--no-ff`, в сообщении — задача), выполняет команды;
  5. всё зелёное — `git push origin <merge>:refs/heads/<base>`; база сдвинулась за время проверки — проверка
     повторяется на новой базе (до 3 раз);
  6. сдаёт результат шага: `pass` (влито или нечего вливать), `changes_requested` (красная команда, конфликт, запрет
     в диффе), `blocked` (ресурс так и не освободился), `needs_coordinator` (коммита нет в репозитории, push отклонён).
     Всё, кроме `pass`, будит координатора, как любой непройденный шаг; слияния нет.
- Лог команд — в сообщениях рана; значения переменных окружения с именами вида `*TOKEN*`, `*SECRET*`, `*PASSWORD*`,
  `*KEY*` вырезаются; токен задачи командам не передаётся.

## Управление маршрутом из чата

`multica issue conveyor pause|resume|disable` принимает команду координатора маршрута, а также агента из
активного личного чата владельца или администратора workspace. Для чата сервер проверяет токен работающего
рана, принадлежность чата этому агенту и человеку, workspace и текущую роль человека. Обычный ран задачи
не получает права управлять чужим маршрутом; завершённый ран и архивный чат права не передают.

Чат не обходит `--revision`, ограничения переходов и права запуска исполнителей. Результат шага
`conveyor result` по-прежнему сдаёт только ран этого шага. Для внешнего управления сначала прочитать
`conveyor get <задача> --output json`, затем передать актуальную ревизию в изменяющую команду.

## `.multica/acceptance.json`

```json
{
  "base": "main",
  "commands": ["make check", "pnpm exec playwright test"],
  "timeout_seconds": 1500,
  "env": {"E2E_LOCK_WAIT": "0"},
  "busy_exit_codes": [75],
  "wait_poll_seconds": 60,
  "wait_max_seconds": 7200,
  "diff_guard": [": any\\b", "as unknown as", "@ts-(?:ignore|expect-error)", "eslint-disable"]
}
```

- `base` — пусто: ветка по умолчанию у origin.
- `timeout_seconds` — на одну попытку одной команды; ожидание занятого ресурса в него не входит.
- `busy_exit_codes` — «общий ресурс занят»: команда повторяется через `wait_poll_seconds`, не дольше
  `wait_max_seconds`, потом шаг сдаётся с `blocked`.
- `diff_guard` — регулярные выражения для добавленных строк; не задан — список выше, `[]` — проверки нет.
- Секреты в файл не пишутся: команды наследуют окружение демона (и его git-доступ).

Файл меняется тем же PR, что и код, и проходит review вместе с ним.

### Режим `ci`

```json
{"base": "main", "mode": "ci", "wait_poll_seconds": 60, "wait_max_seconds": 1800}
```

Для репозитория с CI вливает платформа (в форке — автослияние GitHub после обязательных проверок). Приёмка с
`"mode": "ci"` не сливает, не пушит и не запускает `commands`: она обновляет `origin/<base>` и ждёт, пока закреплённый
коммит станет его предком. Попал в базу — `pass`, задача идёт дальше. Не попал за `wait_max_seconds` (по умолчанию
1800; PR открыт, закрыт без слияния, проверки красные) — `blocked`, шаг не завершается. Слияние должно быть merge-коммитом
(`gh pr merge --auto --merge`): squash и rebase оставляют закреплённый SHA вне базы. Неизвестный `mode` —
`needs_coordinator`. Режим включается только файлом в самом репозитории; без файла поведение прежнее.

## Локальный репозиторий без remote

Репозиторий, живущий только на хосте демона, записывается в репозитории workspace как `file:///абсолютный/путь`
(API принимает такие URL наравне с http(s) и ssh). Чтобы worktree исполнителей называли его тем же URL, `origin`
самого репозитория указывает на него же (`git remote add origin file:///…`). Шаг вливает push в него; у репозитория с
рабочей копией на базовой ветке нужен `git config receive.denyCurrentBranch updateInstead`, и рабочая копия на базе
должна быть чистой — иначе push отклонится и шаг сдастся с `needs_coordinator`.

Путь рабочей копии в `artifact.repo` шаг сам приводит к `origin` копии, а без него — к `file://` основного
репозитория worktree.

Если хост оборачивает git для агентов и запрещает им пуш в базовые ветки, обёртка должна пропускать пуш, чей
непосредственный родитель — процесс `multica workflow accept`: шаг зовёт git напрямую, а команды приёмки идут
через shell и пропуска не получают.

## Маршрут задачи и шаблон сквада

При назначении задачи скваду маршрут берётся из `metadata.route` самой задачи, а если его нет — из шаблона сквада.
Так лидер, раскладывая эпик, пишет у каждой задачи своего исполнителя dev, а стадии и назначение идут без него.

## Права на push

Демон вливает теми же учётными данными git хоста, которыми клонирует (ключ деплоя или credential helper
пользователя демона). На каждом хосте, где Приёмщик может получить ран, у этого пользователя должен быть push в
базовую ветку репозитория. Защита ветки на GitHub, требующая PR, такой push отклонит — шаг сдастся с
`needs_coordinator` и причиной.

## Настройка

```sh
# маршрут без accept: сервер добавит приёмку сам, если в маршруте есть review
multica squad update "Разработка" --route "dev:Бэкенд,qa:Тестировщик,review:Техдиректор,close:Тимлид"
```

Задачи, у которых в маршруте есть `accept`, сторож (`multica-conveyor` ≥ `route-accept-step`) не вливает и лидеру о
них не пишет.

## Выкладка и откат

Нужны новый backend (правила шага) и новый `multica` на хостах демонов (runtime и команда `accept`). Схема
не меняется. Пакета установки у этапа нет: backend собирается и ставится пакетом `deploy/stt-models`
(`build-package.sh --revision <SHA>`), демоны обновляются штатно (новый `multica`, перезапуск демона).

Откат: выключить runtime на демонах (`MULTICA_ACCEPT_RUNTIME=off`) — сервер перестанет добавлять приёмку; явный `accept:…` убрать из шаблона сквада (`multica squad update … --route …`) и с задач
(`multica issue conveyor disable` / `enable` без `accept`) — дальше вливает сторож, как раньше; затем вернуть
прежние backend и `multica`. Выключить runtime на хосте без отката — `MULTICA_ACCEPT_RUNTIME=off`.
