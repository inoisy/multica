# Шаг `accept`: приёмка и слияние маршрутом multica

Этап 1 ТЗ `tz-conveyor-in-multica.md`. Шаг маршрута `accept` проверяет коммит, который прошли dev, qa и review,
поверх текущей базовой ветки и вливает ровно проверенный merge-коммит прямым push. Выполняет его демон multica
без модели.

## Как это устроено

- Каждый демон регистрирует runtime `accept` (исполняемый файл — сам `multica`). Выключить на хосте:
  `MULTICA_ACCEPT_RUNTIME=off` в окружении демона.
- Агент «Приёмщик» — обычный агент workspace на runtime `accept` любого демона. Профиль модели ему не нужен.
- Маршрут: `…,review:<ревьюер>,accept:Приёмщик,close:<координатор>`. `accept` стоит один раз, прямо перед `close`,
  и только после `review`; сервер проверяет это при включении маршрута и при сохранении шаблона сквада.
- Ран шага запускает `multica issue conveyor accept`. Команда:
  1. берёт принятый коммит маршрута (`accepted_commit`) и репозиторий с веткой из прошедшего результата,
     который этот коммит назвал (`artifact.repo`, `artifact.branch` шага dev — **`artifact.repo` должен быть
     URL репозитория**, как для `multica repo checkout`);
     Путь локальной рабочей копии (как его пишут исполнители, работающие в worktree) приводится к репозиторию
     workspace: `origin` копии, а без него — основной репозиторий worktree;
  2. получает свежую копию через кэш репозиториев демона;
  3. читает `.multica/acceptance.json` из самого коммита;
  4. проверяет дифф, сливает коммит поверх `origin/<base>` (`--no-ff`, в сообщении — задача), выполняет команды;
  5. всё зелёное — `git push origin <merge>:refs/heads/<base>`; база сдвинулась за время проверки — проверка
     повторяется на новой базе (до 3 раз);
  6. сдаёт результат шага: `pass` (влито), `changes_requested` (красная команда, конфликт, запрет в диффе),
     `blocked` (ресурс так и не освободился), `needs_coordinator` (нет описания приёмки, нет коммита, push отклонён).
     Всё, кроме `pass`, будит координатора, как любой непройденный шаг; слияния нет.
- Лог команд — в сообщениях рана; значения переменных окружения с именами вида `*TOKEN*`, `*SECRET*`, `*PASSWORD*`,
  `*KEY*` вырезаются; токен задачи командам не передаётся.

## `.multica/acceptance.json`

```json
{
  "base": "main",
  "commands": ["make check", "pnpm exec playwright test"],
  "timeout_seconds": 1500,
  "env": {"E2E_LOCK_WAIT": "0"},
  "busy_exit_codes": [75],
  "wait_poll_seconds": 60,
  "wait_max_seconds": 7200,
  "diff_guard": [": any\\b", "as unknown as", "@ts-(?:ignore|expect-error)", "eslint-disable"]
}
```

- `base` — пусто: ветка по умолчанию у origin.
- `timeout_seconds` — на одну попытку одной команды; ожидание занятого ресурса в него не входит.
- `busy_exit_codes` — «общий ресурс занят»: команда повторяется через `wait_poll_seconds`, не дольше
  `wait_max_seconds`, потом шаг сдаётся с `blocked`.
- `diff_guard` — регулярные выражения для добавленных строк; не задан — список выше, `[]` — проверки нет.
- Секреты в файл не пишутся: команды наследуют окружение демона (и его git-доступ).

Файл меняется тем же PR, что и код, и проходит review вместе с ним.

## Локальный репозиторий без remote

Репозиторий workspace может быть путём на хосте демона (`/home/agents/…/service`). Шаг вливает push в него самого;
у репозитория с рабочей копией на базовой ветке нужен `git config receive.denyCurrentBranch updateInstead`, и рабочая
копия на базе должна быть чистой — иначе push отклонится и шаг сдастся с `needs_coordinator`.

## Маршрут задачи и шаблон сквада

При назначении задачи скваду маршрут берётся из `metadata.route` самой задачи, а если его нет — из шаблона сквада.
Так лидер, раскладывая эпик, пишет у каждой задачи своего исполнителя dev, а стадии и назначение идут без него.

## Права на push

Демон вливает теми же учётными данными git хоста, которыми клонирует (ключ деплоя или credential helper
пользователя демона). На каждом хосте, где Приёмщик может получить ран, у этого пользователя должен быть push в
базовую ветку репозитория. Защита ветки на GitHub, требующая PR, такой push отклонит — шаг сдастся с
`needs_coordinator` и причиной.

## Настройка

```sh
multica agent create --name "Приёмщик" --runtime-id <id runtime accept нужного демона>   # или в интерфейсе
multica squad update "Разработка" --route "dev:Бэкенд,qa:Тестировщик,review:Техдиректор,accept:Приёмщик,close:Тимлид"
```

Задачи, у которых в маршруте есть `accept`, сторож (`multica-conveyor` ≥ `route-accept-step`) не вливает и лидеру о
них не пишет.

## Выкладка и откат

Нужны новый backend (правила шага) и новый `multica` на хостах демонов (runtime и команда `accept`). Схема
не меняется. Пакета установки у этапа нет: backend собирается и ставится пакетом `deploy/stt-models`
(`build-package.sh --revision <SHA>`), демоны обновляются штатно (новый `multica`, перезапуск демона).

Откат: убрать `accept:…` из шаблона сквада (`multica squad update … --route …`) и с задач
(`multica issue conveyor disable` / `enable` без `accept`) — дальше вливает сторож, как раньше; затем вернуть
прежние backend и `multica`. Выключить runtime на хосте без отката — `MULTICA_ACCEPT_RUNTIME=off`.
