# Выкладка маршрута задачи (конвейер)

Пакет заменяет только контейнер backend живого стека multica. PostgreSQL, frontend
и daemon хоста не останавливаются, не пересоздаются и не получают сигналов.

## Что в релизе

Opt-in маршрут одной задачи: исполнитель сдаёт шаг структурированным результатом, а сервер
в транзакции, закрывающей его ран, решает переход и ставит ран следующего шага. Обычные задачи,
будильники людей и комментарии людей работают как раньше. Схема меняется только добавлением:
таблицы `issue_conveyor`, `issue_conveyor_event` и колонка `agent_task_queue.conveyor_action_id`
(миграции 564–574, индексы — отдельными `CONCURRENTLY`-файлами).

## Сборка пакета (без root и docker)

```sh
deploy/stt-258/build-package.sh --revision <SHA> --daemon-pid <PID daemon>
```

Создаёт `/home/agents/deploy/stt-258-<SHA9>/`: `source.tar.gz` (то, из чего собирается образ),
`manifest.json` (ревизия, SHA-256 архива, тег образа, диапазон миграций, защищаемые сервисы),
скрипты. Образ собирается при установке из этого архива: digest локальной сборки (`image ID`)
записывается в `state.env` каталога отката. Если образ собран заранее и лежит в реестре,
`manifest.image.reference` с digest заменяет локальную сборку.

## Установка (root)

```sh
sudo /home/agents/deploy/stt-258-<SHA9>/preflight.sh --manifest /home/agents/deploy/stt-258-<SHA9>/manifest.json   # ничего не меняет
sudo /home/agents/deploy/stt-258-<SHA9>/install.sh   --manifest /home/agents/deploy/stt-258-<SHA9>/manifest.json
```

`install.sh` сам запускает preflight и затем:

1. находит стек по меткам запущенного контейнера backend (проект, каталог, compose-файлы);
2. теггирует текущий образ (`multica-backend:pre-stt-258-<суффикс>`), создаёт `/var/backups/multica-stt-258.<суффикс>/`
   с `state.env`, `rollback.sh`, `manifest.json`;
3. собирает образ из `source.tar.gz` (`COMMIT` = первые 9 символов ревизии);
4. применяет миграции новым образом, пока старый backend продолжает работать (старый код новых таблиц не читает);
5. пересоздаёт только backend (`up -d --no-deps --pull never`), ждёт `/health` с новым коммитом;
6. сверяет контейнеры postgres/frontend и PID daemon с записанными до замены.

Коды выхода: `0` готово; `2` новый backend не ответил — прежний образ возвращён автоматически;
`3` backend заменён, но набор PID daemon или контейнер защищённого сервиса изменился (смотрите вывод).

Замена переживёт ручной `docker compose up` без override, только если образ записан в окружение стека
(`MULTICA_BACKEND_IMAGE` / `MULTICA_IMAGE_TAG`); установщик `.env` не трогает и печатает напоминание.

## Откат

```sh
sudo /var/backups/multica-stt-258.<суффикс>/rollback.sh [--force]
```

Возвращает прежний образ только для backend и ждёт `/health` с прежним коммитом. Таблицы
`issue_conveyor*` и колонка остаются: прежний код их не читает, а журнал не теряется. У прежнего
образа нет эндпоинтов маршрута, поэтому новый маршрут включить нельзя до новой установки.
Пока у каких-то задач маршрут включён, откат отказывается без `--force`: сначала
`multica issue conveyor disable <задача>`.

## Включение на одной задаче

```sh
multica issue conveyor enable <задача> --route "dev:Бэкенд,qa:Тестировщик,close:Тимлид"   # или metadata.route
multica issue conveyor get <задача>
multica issue conveyor events <задача>
```

Исполнитель шага сдаёт результат `multica issue conveyor result <задача> --file result.json`
(формат в handoff-ноте рана). Координатор получает ран при возврате, остановке, падении и в конце.
`pause|resume --step <шаг>|disable` меняют маршрут; `multica issue rerun <задача> --task <ран>`
повторяет упавший шаг ровно одним ран-преемником.

Статус задачи меняется вместе с доставкой рана: `dev` → `in_progress`, `qa` → `qa`,
`review` → `review`, финальный `close` → `in_review`. При возврате на `dev` статус снова
`in_progress`. Закрытые задачи (`done`/`cancelled`, включая пользовательские терминальные
статусы) конвейер не открывает. Если доставка отложена, статус и `metadata.step` остаются
на последнем доставленном шаге; актуальное ожидающее действие видно в `conveyor get|events`.

При включении маршрута отсутствующие пользовательские статусы `qa`/`review` создаются
в категории `started`, только если включивший маршрут — owner/admin workspace.
Обычный участник может включить маршрут с уже настроенными статусами. Существующие названия
и цвета сохраняются; архивный статус или ключ в другой категории отклоняет включение.
Если статус архивировали до доставки соответствующего шага, действие остаётся `pending`
с причиной в журнале и ран не создаётся. Сначала исправьте каталог статусов или отключите маршрут.

При сбое рана явный `failure_reason` имеет приоритет над текстом ошибки. Только штатные
`agent_error.provider_quota_limit` и `agent_error.provider_capacity_or_rate_limit` передают
восстановление обработчику провайдеров. Старые записи без причины классифицируются через
`pkg/taskfailure`; остальные ошибки вызывают координатора, даже если текст содержит «429»,
«disk quota exceeded» или «rate limit».

## Что смотреть при сбое

- `multica issue conveyor events <задача>`: у каждого входа есть решение; действие со `state=pending`
  и причиной в `reason` — ран ещё не создан (агент недоступен, нет прав у включившего), его дожимает
  задача планировщика `issue_conveyor_delivery` раз в 30 секунд;
- маршрут в `active` без рана и без отложенного действия через 5 минут сам уходит координатору;
- `docker compose logs backend | grep conveyor`.
