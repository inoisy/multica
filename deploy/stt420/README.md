# STT-420: прод-копия для QA и пакет операторской выкатки

Пакет устанавливает закреплённый backend/web и сохраняет данные для отката.
Workflow STT-420 остановлен по поручению Евгения 25.10.2026: остаток закрывает
Техдиректор с проверками затронутых изменений. `acceptance.json` должен ссылаться
на фактический итоговый отчёт с SHA, объёмом проверок и ограничениями; результаты
предыдущих SHA указываются отдельно. Наличие пакета само по себе не означает
успешную установку в прод.

## Прод-копия для STT-424: одно действие оператора

Из проверенной рабочей копии ветки `t-12345-model-ui` оператор на прод-хосте:

```sh
sudo python3 deploy/stt420/snapshot.py \
  --source-revision aebbec7876b9f187bd3f5d78ef357e6770c33b63 \
  --out /var/backups/multica-qa-snapshot \
  --owner agents
```

Нужно право выполнить **эту команду** с Docker/БД от оператора. Давать агенту
Docker group, root-shell или доступ к production `.env` не требуется. Если текущий
health SHA отличается от зафиксированного исходного — экспорт остановится;
оператор должен сверить актуальный исходный SHA, а не обходить эту проверку.
Каталог назначения должен отсутствовать; частичный неудачный экспорт не использовать.

`snapshot.py` не останавливает сервисы, не меняет схему/данные и не запускает
выкатку. Он держит read-only repeatable-read транзакцию с `pg_export_snapshot()`,
делает `pg_dump -Fc --snapshot` из того же снимка, затем закрывает транзакцию.
`manifest.json` содержит UTC/T из БД, snapshot ID, SHA256 дампа, версии PostgreSQL,
extensions, список миграций, исходный SHA и image IDs. T — начало транзакции,
зафиксировавшей снимок, а не время окончания выгрузки. Сервисы должны сохранить
те же container IDs в течение экспорта. Допустимая исходная схема — 596.

`database.dump` и `manifest.json` получают владельца `agents`, файлы 0600,
каталог 0700. В задачу передать путь к manifest и его T/checksum; **не прикладывать
дамп и не публиковать JSON прогнозов**. На отдельном QA-хосте перед восстановлением
сверить SHA256 дампа с manifest. Нужны PostgreSQL с `pg_bigm`, Redis, GTK для Electron;
для полной проверки Cursor — ядро Linux >=6.9 с `PIDFD_THREAD`. Изолированная
копия не должна иметь доступ к прод-сервисам и credentials. Сначала на ней выполнить
baseline PreviewChoice при T, up/idempotency, новый PreviewChoice/diff, ограниченный
down 612…597 и исходный PreviewChoice/diff; затем остальные критерии STT-424.
Завершить успешные QA и review закреплённого SHA до подготовки acceptance ниже.

## Сборка релизного пакета после исправлений

Пакет рассчитан на действующий backend `aebbec787` (v0.7.0), схему 596,
Compose `/opt/multica/docker-compose.selfhost.yml` и его фактические overrides
из меток контейнера. Цель — схема 612. Скрипты `deploy/stt-models` (575–585)
и `deploy/analytics-web` этот релиз не устанавливают.

Из чистой рабочей копии, Go в PATH, без root:

```sh
python3 deploy/stt420/build-package.py --revision <SHA40> --out <новый-каталог>
```

В пакете полный git archive, SHA-256 каждого файла, manifest, статические Linux/amd64
server/migrate/CLI и два экспортёра PreviewChoice. Исходный экспортёр фиксирован
на `40a8b5ff6c4ba5cec81d29650ceff63e0cb67763`; новый — на SHA релиза.
Пакет не содержит credentials или дампов. Сверить SHA256SUMS перед root-запуском.
Python >=3.12, Docker Compose/buildx (`stand-build`), 10 GiB свободного места для
образов и не менее четырёх размеров БД в `/var/backups` необходимы на сервере.

## Команды оператора

Распаковать архив, открыть итоговый отчёт и запустить из каталога пакета:

```sh
sudo sh ./install.sh
```

`install.sh` проверяет SHA256SUMS, выполняет `check`, затем `install` с
приложенным `acceptance.json`. При отказе проверки установка не начинается.
При нестандартных путях передать `--compose`, `--api`, `--web`; они идут
в обе команды. В логе сохранить строку `STATE=...` для статуса и отката.
Скрипт не обновляет демон и не запускает STT-425.

Те же действия по отдельности:

```sh
sudo python3 /путь/к/пакету/deploy.py check
sudo python3 /путь/к/пакету/deploy.py install --acceptance /путь/к/acceptance.json
```

`acceptance.json` заполняется по фактическим проверке и финальному разбору
закреплённого SHA, в Workflow или в чате:

```json
{
  "revision": "<полный SHA40 пакета>",
  "qa": {"passed": true, "report_url": "https://<ссылка-на-успешную-QA>"},
  "review": {"passed": true, "report_url": "https://<ссылка-на-успешное-review>"}
}
```

Установщик проверяет совпадение SHA и наличие обоих отчётов. Он не обращается
к Workflow и не подтверждает подлинность отчётов: это ответственность оператора.
Файл нельзя заполнять авансом или по результатам одной сборки пакета.

`check` только читает: проверяет hashes, текущий SHA, точный набор миграций,
Compose, единственные backend/frontend/postgres, builder, свободное место и PID
защищённого демона. Дрейф останавливает установку; разрешённые базовые значения
не расширять вслепую.

`install` печатает `STATE=/var/backups/multica-stt420.XXXXXXXX` до начала сборки.
Сохраняет версии/контейнеры/Compose, прежние image IDs с отдельными tags, `.env`
и собственную копию пакета. Собирает backend/web из проверенного archive;
web Dockerfile получает только `NODE_OPTIONS=--max-old-space-size=6144` для сборки.
Образы помечены полным SHA и устанавливаются по immutable image ID.

После сборки повторяет preflight, останавливает только frontend/backend, делает
консистентный `pg_dump -Fc` с manifest: UTC/T, checksum, PostgreSQL/extensions,
исходные миграции и SHA. PostgreSQL, его volume и демон не перезапускаются.
На время проверки копии и миграций API/web недоступны; идущие агентские процессы
продолжают работу, доставка их отчётов может задержаться.

Копия восстанавливается в отдельный контейнер того же PostgreSQL image ID,
`--network none`, без опубликованных портов и доступа к рабочим volumes.
Проверки: исходный PreviewChoice всех контекстов STT при фиксированном T →
up до 612 → повторный up → новый PreviewChoice/diff → down **только 612…597** →
исходный PreviewChoice/diff и точное сравнение schema-only dump.
Исторические refusal rows перед baseline не пересчитываются. Допускается одно
отличие — принятое в STT-424 исправление: окно аккаунта на 100 % без флага
`limit_reached` считается израсходованным (спецификация §3.4). Новый экспортёр
помечает такие контексты `ACCEPTED` (`diff --accept provider-full-window`):
строка была доступна, стала `limited` с `reason_code=provider_limit` и сроком,
а остальные отличия контекста — только следствия (выбранная строка, позиция,
причина, ожидание до сброса этого окна). Любое другое отличие (`DIFF`) и любое
отличие после down останавливают установку до живой миграции и возвращают
старые сервисы. Обезличенный вывод обоих diff записывается в `state.json`
(`rehearsal.preview_diff`, `rehearsal.rollback_preview_diff`) и при отказе.
Это проверка конкретного dump; полную QA STT-424 она не заменяет.

После успеха на копии: живой up → проверка всех миграций → новые backend/web →
health с SHA, HTTP `/login` и `/profiles`, image IDs, неизменность PostgreSQL/PID
демона. В state записываются deployed SHA, UTC и результаты; dump и JSON прогнозов
остаются root-only и в задачу не отправляются. При ошибке после живой миграции
автооткат выполняет ограниченный down, затем возвращает оба прежних образа.

Управлять стеком далее с **полным набором Compose-файлов из labels/state и новым
`STATE/new-images.json`**, иначе ручной compose по одному старому файлу может
вернуть прежние образы. State не удалять в течение окна отката.

## Проверка и откат

```sh
sudo python3 STATE/package/deploy.py status --state STATE
sudo python3 STATE/package/deploy.py rollback --state STATE
```

Ручной откат отклоняет чужие образы, иной schema version и изменённый Compose.
Останавливает только backend/frontend, выполняет down 612…597 (переносит текущие
правки личных профилей, пулов и caps в старую схему), возвращает old image IDs,
проверяет прежний health. Dump автоматически поверх новых записей не льётся.
Откат не восстанавливает сам бинарник CLI: новый демон совместим со старым API;
он и его backup указаны в `state.cli`. При необходимости вернуть CLI — в простое
поставить `STATE/multica-before` на записанный `state.cli.target` и перезапустить
только `multica-agents`. Остановить daemon с активными ранами запрещено.

Если процесс оператора был прерван SIGKILL, phase/handles в `STATE/state.json`;
для фаз stopped/migrating сначала изучить журнал, завершить ограниченный down при
необходимости и вернуть образы через `STATE/old-images.json`. Не применять полный
`migrate down` (он откатывает все миграции). Аварийное восстановление dump —
отдельное решение оператора с оценкой записей после snapshot; штатный откат выше.
Для уборки изолированной копии после аварии точное имя в `rehearsal_container`;
контейнер штатно удаляется в finally, его файлы в `STATE/rehearsal-data` сохраняются.

## CLI и демон — отдельная передача после завершения рана

Backend/web устанавливаются с работающим прежним демоном. Его обновление из
выполняемого им рана не запускается. После завершения текущего рана оператор:

```sh
sudo python3 STATE/package/install-cli.py --state STATE
```

Скрипт проверяет local daemon health/PID юнита, ноль активных ранов/неотправленных
отчётов и ноль running/dispatched в БД. Затем приостанавливает backend как барьер
новым claim, повторяет проверку простоя, останавливает только точный systemd-юнит,
сохраняет старый executable, атомарно ставит новый, возвращает backend и daemon.
При неуспехе возвращает прежний бинарник. При занятости ничего не обновляет;
его нельзя запускать с принудительным обходом проверки простоя.

## Проверки пакета

```sh
python3 -m unittest discover -s deploy/stt420 -p 'test_*.py' -v
git diff --check
```

Полные Go/frontend/desktop/v2 и визуальные критерии STT-424 учитываются отдельно.
После фактической установки проверить страницы в браузере обе темы × 1440/375,
формы/select и авторизованные API. Smoke установщика проверяет доступность,
но не заменяет эти сценарии. STT-425 не запускается этим пакетом.
